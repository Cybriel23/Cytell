## Executive Summary
Activity is high going into the US Thanksgiving weekend, when staffing is thin and attackers like to strike. Four things need attention today. On incidents, a breach of a **CIA/ODNI unclassified OSINT system** follows the still-unexplained **FBI NCIC** intrusion. Physical-impact incidents at **Peninsula Energy's Wyoming uranium mine** and on commercial tankers point to growing operational risk. ## 1. Risk Watch

### 1.1 Drupal core installer RCE CVE-2026-132165 exploited, KEV deadline 27 Nov (ONGOING)
Drupal's **SA-CORE-2026-017** (rated "Highly critical", 20/25) covers a fail-open flaw in `install.php`. Under certain conditions it lets an unauthenticated attacker re-run the installer on a live site, which leads to site takeover or code execution. Some exploit paths are blocked when the web server cannot write to or chmod `settings.php`, but not all of them. Affected versions are Drupal 10 before **10.6.22**, 11.0–11.3 before **11.3.22**, and 11.4 before **11.4.13**. Branches 11.2.x and earlier and 10.5.x and earlier are end-of-life and get no fix. The Drupal Security Team has reports of exploitation on live sites since **19 Nov 19:00 UTC**. CISA added the CVE to KEV on 24 Nov with a **27 Nov** due date.
**Action:** Upgrade to a fixed release today. On every site, harden or block access to `/core/install.php`, and remove web-server write permission on `sites/*/settings.php`. Hunt web logs for requests to `install.php` since 19 Nov, and look for unexpected admin accounts, a reset site configuration or new modules. Sites on EOL branches need to migrate or be put behind a WAF rule that blocks the installer.
**Sources:** [Drupal SA-CORE-2026-017](https://www.drupal.org/sa-core-2026-017) · [CISA KEV catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) · [Canadian Centre for Cyber Security AV26-1186 Update 1](https://www.cyber.gc.ca/en/alerts-advisories/drupal-security-advisory-av26-1186)

### 1.2 VMware VMSA-2026-0011: second critical vCenter vmdir auth bypass, CVE-2026-123903 (CVSS 9.8)
On 24 Nov Broadcom shipped its third critical bundle in a week, fixing **23 flaws** across ESX, vCenter, Workstation, Fusion and Avi Load Balancer. The most serious is **CVE-2026-123903 (CVSS 9.8)**, an authentication bypass in VMware Directory Service (vmdir) that any attacker with network access to vCenter can reach. The bundle also includes **CVE-2026-123904** (archive-processing file write that can lead to code execution, CVSS 7.5) and three vmdir DoS bugs. Broadcom says the new bug is distinct from **CVE-2026-123890**, the vmdir bypass that the suspected China-nexus actor **ARMORY CASTLE** exploited as a zero-day from early September. No exploitation of the new CVE is reported. Still, a second pre-auth bug in the same component is just what that actor's patch-diffing playbook (and AI-assisted n-day tooling) is likely to target quickly. Fixed versions: vCenter **8.0 U3m**, VCF/VVF **9.1.2** and **9.0.2.0300**, VCF **5.2.5**. vCenter 7.0 customers need Broadcom extended support.
**Action:** Patch vCenter before the holiday weekend and restrict access to vCenter ports to the management network. If you have not yet done the CVE-2026-123890 compromise assessment (STS/SSO signing certificates, unexpected local SSO accounts, vmdir logs), do it before or while patching.
**Sources:** [The Hacker News](https://thehackernews.com/2026/11/vmware-vcenter-hit-by-another-critical.html) · [The Register](https://www.theregister.com/virtualization/2026/11/25/this-could-mess-with-thanksgiving-says-vmware-as-it-drops-third-critical-patch-bundle-in-a-week/5312017) · [SecurityWeek](https://www.securityweek.com/vmware-updates-patch-critical-esx-vcenter-vulnerabilities/) · [Canadian Centre for Cyber Security AV26-1203](https://www.cyber.gc.ca/en/alerts-advisories/vmware-security-advisory-av26-1203)

### 1.3 Provider-side secret exposure: Radware Cloud WAF, Rackspace Spot, Azure APIM Classic (ROTATE NOW)
Three providers disclosed incidents in which customer secrets may have been exposed. In each case, the provider's own fix does not invalidate credentials that were already taken.
- **Radware:** On **19 Nov** an internal Cloud WAF management API that was reachable from the internet without authentication was accessed. It exposed customer contact details and, for some customers, **log-export credentials (AWS S3 keys, Azure Blob keys/SAS tokens, SFTP credentials)**. Radware detected it about 10 hours later. Some customers have seen AWS alerts about an unfamiliar IP probing their log buckets. These details come from a root-cause report BleepingComputer obtained. Radware had not made a public statement at the time of writing.
- **Rackspace Spot (Kubernetes):** Attackers used compromised credentials on **17 Nov**. They could create pods, read cluster Secrets and list nodes and volumes. Rackspace is shutting the service down on **8 Dec (17:00 CT)**. IOCs: **23.224.79.106**, the range **23.224.0.0/15**, and pod/object name prefixes `i1`, `glm-`, `probe`.
- **Azure API Management Classic:** Microsoft (Service Health tracking ID **MZK9-GH0**) identified the issue on 18 Nov and mitigated it on 19 Nov. Exposed items may include Named Values, IdP/OIDC client secrets, subscription keys and management tokens. Norway's NSM links the issue to the **Equinor** and **Skagerak Energi** incidents. v2 tiers are not affected.
**Action:** Radware customers: rotate log-export credentials and review S3/Blob/SFTP access logs back to 19 Nov. Rackspace Spot customers: treat kubeconfigs, API and refresh tokens and every cluster Secret as compromised, hunt for the IOCs above, and migrate before 8 Dec. APIM Classic customers: rotate secrets at the system that issued them (changing the value in APIM alone is not enough), confirm builds ≥ **0.52.31936** / **0.53.31938**, and review access before 19 Nov.
**Sources:** [BleepingComputer: Radware](https://www.bleepingcomputer.com/news/security/radware-discloses-breach-exposing-customer-cloud-access-keys/) · [BleepingComputer: Rackspace Spot](https://www.bleepingcomputer.com/news/security/rackspace-shuts-down-spot-cloud-platform-after-security-breach/) · [Network World: Azure APIM](https://www.networkworld.com/article/4252523/attackers-exploited-an-azure-api-management-flaw-to-steal-secrets-microsoft-warns-2.html) · [Help Net Security](https://www.helpnetsecurity.com/2026/11/24/azure-apim-vulnerability-credential-theft/)

### 1.4 Idunno.AntiCsrf CVE-2026-131914: unauthenticated ASP.NET RCE, no patch, now in KEV (ONGOING)
This is a follow-up from yesterday. CISA added **CVE-2026-131914 (CVSS 9.3)** to KEV on 24 Nov with a **27 Nov** due date. **watchTowr** reports in-the-wild probing in its honeypots with compiled .NET gadget payloads, which confirm a vulnerable target by triggering a redirect to a unique URL. Mandiant (MNDT-2026-0048) has also observed active exploitation. The module, `Idunno.AntiCsrf.dll` versions 0.9.1.0 and 0.9.1 Beta, was abandoned in 2008. It deserializes the CSRF form token with an unkeyed `ObjectStateFormatter` and no MAC check. A single POST with any non-empty CSRF cookie gives code execution as `w3wp.exe`. There is no patch and none is expected.
**Action:** Search `Web.config` files and `bin/` folders for `Idunno.AntiCsrf` / `AntiCsrfModule`, and replace the module with the AntiForgery helpers or ViewStateUserKey plus MAC. In IIS logs, look for anomalous POSTs to `.aspx` pages that return 302/500 with high `cs-bytes`. If you suspect compromise, rotate `machineKey` and the database credentials in `Web.config` and `applicationHost.config`, and sweep webroots for webshells.
**Sources:** [The Hacker News](https://thehackernews.com/2026/11/hackers-exploit-critical-aspnet-anti.html) · [Mandiant MNDT-2026-0048](https://github.com/mandiant/Vulnerability-Disclosures/blob/master/2026/MNDT-2026-0048.md) · [CISA KEV catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)
