# ARTEX: The AI Agent That Hacks on Its Own

## TL;DR

ARTEX is an **agentic AI penetration-testing framework** — software that takes a
high-level goal ("get into this cloud tenant and find API keys") and then plans
and carries out the attack steps largely by itself, driven by a large language
model. It was built in China as an open-source tool for authorized security
testing. Within weeks of release it was adopted by cybercriminals and
China-nexus espionage groups, who are now using it to run intrusions faster than
human operators could. This post explains ARTEX for a non-specialist audience
and consolidates the indicators of compromise (IOCs) reported publicly, together
with Cytell's own observations of exposed ARTEX consoles.

---

## What is ARTEX, in plain language?

Most hacking tools do one narrow thing: scan a network, crack a password, send a
phishing email. A human operator chains those tools together and makes the
decisions. ARTEX is different. You give it an objective and some rules, and an
**AI "agent" makes the decisions itself** — it probes a target, interprets what
it finds, picks the next tool to run, and keeps going until it reaches the goal
or gives up. In practice that means an attacker can point it at hundreds of
targets at once and let it work around the clock with little supervision.

A few things make ARTEX notable:

- **It was meant to be legitimate.** Agentic pentest frameworks are a real and
  growing category of defensive tooling, intended for teams testing systems they
  own or are authorized to assess. ARTEX started as an open-source project of
  that kind.
- **It went closed-source on 8 October 2026** after attracting attention, but by
  then forks and backups of the original code were already circulating publicly,
  so the genie was out of the bottle.
- **The operator runs a web console.** Each deployment exposes a management
  interface — by default on **TCP port 8787** — from which the operator steers
  the agents. These consoles are what internet scanners (and Cytell) can see.
- **Much of its on-target "signature" is generated by the AI, not the code.**
  Because an LLM improvises the actual commands, probe names, and test inputs,
  many of the strings defenders see change from run to run. That has real
  consequences for detection (see below).

As of early November 2026, researchers had catalogued **more than 1,600 publicly
exposed ARTEX consoles**, and the FBI issued an advisory warning that the tool is
powering global cyberattacks. The true number of deployments is believed to be
higher.

## How threat actors are using it

Public reporting from Amazon, SentinelOne, Microsoft, Palo Alto Unit 42 and
others describes several overlapping campaigns:

- **Credential and API-key harvesting.** Agents hunt for exposed secrets — cloud
  access keys, AI-model API keys — in code repositories and misconfigured
  services, then validate and abuse them.
- **Cloud tenant intrusion at scale.** In the October 2026 ConnectWise
  supply-chain compromise, the China-aligned actor **Storm-0940** reportedly used
  ARTEX to attempt sign-ins against more than 2,250 Azure tenants.
- **Espionage.** **VAPOR PANDA**, a China-nexus espionage group, began
  ARTEX-enabled intrusions around 17 October 2026, reportedly targeting 200+
  organizations.
- **Financially motivated crime.** Clusters such as **Storm-3358** targeted
  Southeast Asian financial institutions, and other operators hit South Korean
  banks and attempted to defeat cryptocurrency-exchange identity checks using
  deepfakes.

Amazon assessed with moderate confidence that activity it observed was tied to
Chinese-nexus actors.

## Why ARTEX is hard to detect — and what actually works

A word of caution before the IOC list: **most "ARTEX" indicators are weak on
their own.** Independent source analysis shows that many published indicators —
self-identifying user agents like `artex-pentest/1.0`, probe filenames like
`artex-probe-NNNNN`, placeholder test usernames — are produced by the language
model or by the ordinary tools it runs, not hard-coded in ARTEX. They change
between runs, and a fork can rename them in a single commit.

The more durable indicators are **operator-side**: the console title, the
listening port, the authentication realm string, the platform's Chinese "call
blocked" guard message, and the database/environment-variable layout. Even these
are only *supporting* evidence, because a fork can strip them out.

**The most reliable detection is behavioural**, not string-based. Hunt for what
an agent *does*: a single identity triggering a burst of permission-denied
errors across many cloud APIs in seconds; rapid validation sweeps across many
resource types; write-then-delete of tiny storage objects within a second; a web
server process spawning a shell; one application requesting tokens across ARM,
Key Vault, Storage and Graph in a short window. Treat the static IOCs below as a
starting point and a bonus — not as a complete net.

TCP 8787 and identified **66 live hosts**. All returned HTTP 401 behind one of
two authentication variants: 15 exposed the console directly (response header
`X-Artex-Auth: basic`) and 51 sat behind an nginx wrapper advertising
`WWW-Authenticate: Basic realm="Artex Restricted"`. The ARTEX keyword appears in
the service banner but **not** in the HTML title or body, so title/HTML scan
queries miss them; the working pivot is the Shodan query `artex port:8787`.

Infrastructure is entirely rented VPS/cloud (top networks: Tencent Cloud,
HostPapa, CTG Server, Cogent); 62 of 66 served plain HTTP. These are **suspected
ARTEX C2/console hosts identified by banner match** — not confirmed intrusions —
